

	# Part 1: Summary — The Model Context Protocol

Large language models are powerful but isolated: they only know what was in their training data and cannot act on the outside world on their own. Before MCP, developers had to build a custom integration for every tool or data source, which was brittle and hard to scale. The Model Context Protocol (MCP), released by Anthropic in November 2024, solves this with one open, model-agnostic standard for connecting AI applications to tools and data, turning an N×M integration problem into N+M. MCP has three roles. The **Host** is the AI application the user interacts with, such as Claude Desktop or a custom agent. Inside the host, an MCP **Client** maintains a one-to-one connection with a single server and relays messages. The **Server** is a separate program that exposes capabilities: tools the model can call, resources it can read, and prompt templates. Because clients discover a server's tools at runtime, new servers can be added without changing the host's code. The article stresses that MCP is an integration layer, not an agent framework, and notes a key limitation: adding tools does not guarantee the model will use them well, since that depends on clear tool descriptions.

## Exploring an Existing Server: Fetch

I explored the Fetch MCP server, one of the official reference servers in the modelcontextprotocol/servers repository. It lets a model retrieve a web page and returns it as Markdown, which is far easier for an LLM to read than raw HTML. The server exposes a single tool, `fetch`, with typed arguments: `url`, `max_length`, `start_index` for reading long pages in chunks, and `raw` to return the original HTML. Measured against the tool design principles from class, it scores well on a **well-defined interface** and **predictable behavior**: the name is clear, the arguments are documented, and the output format is consistent. It also respects `robots.txt` for model-initiated requests. However, it is less strong on **isolated functionality**. Describing it honestly requires "and": it downloads the page *and* converts it to Markdown *and* handles pagination. A cleaner design could split this into a `fetch_page` data tool and a separate `convert_to_markdown` tool. In practice, bundling them is a reasonable trade-off, since the model almost always wants the converted version, and fewer tools means fewer chances to pick the wrong one.
