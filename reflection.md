# Reflection

I drew the line between my tools based on one question: does the tool only read, only write, or coordinate? `get_forecast` only reads weather data and never changes anything, `save_trip` only writes to the trip list and never looks up weather, and `plan_trip` contains no weather or saving logic of its own; it simply calls the other two in order and turns the forecast into a short note. The hardest decision was `plan_trip` itself. My first version only checked the weather on the arrival day, which I realized was not useful for a real trip, so I extended it to check every day of the stay. I kept this as one tool rather than splitting it, because "plan a trip" is still a single goal from the user's point of view. To avoid duplicated code, I put the real logic in plain helper functions that both the individual tools and the orchestration tool reuse.

Three tools felt like the right number for this use case: each maps to a clear type of user request ("what's the weather?", "save this trip", "plan a trip for me"), and in testing the agent consistently picked the correct one based on the tool descriptions alone. Adding more tools would increase the chance of the model choosing the wrong one, which the MCP article lists as a real limitation. Building it also showed me that tool design is only half the work; the client configuration mattered just as much, since the SDK's default 5-second timeout and hidden error messages initially made working tools look broken. As next steps, I would add a `list_trips` resource so the agent can read saved trips, a `delete_trip` action tool, and support for longer trips using historical climate averages beyond the 15-day forecast limit.
